## 1. 基調講演（14:00～15:00）

### 1.1 Google Cloud

**Google Cloudのインフラとデータベース最新動向。AIが使う基盤、AIで作る基盤。**

登壇者：Google Cloud 安原 稔貴 氏

#### AI時代の基盤に求められる2つの視点

AI時代のインフラ・データベースについて、「AIが使う基盤」と「AIで作る基盤」の2つの視点が示された。

| 視点 | 主な内容 |
|---|---|
| AIが使う基盤 | 社内外のAIエージェントが24時間365日アクセスできる基盤 |
| AIが使う基盤 | AIエージェントが解釈できるデータの整備 |
| AIが使う基盤 | AIエージェントが生成したコードを安全に実行する環境 |
| AIで作る基盤 | 環境移行・モダナイゼーションにおけるAIエージェントの活用 |
| AIで作る基盤 | システム運用におけるAIエージェントの活用 |

AIを稼働させるための基盤整備と、基盤の移行・構築・運用にAIを活用する取り組みを、両面から進める方向性が紹介された。

#### TAPの取り組みの変化

Tech Acceleration Program（TAP）では、インフラの刷新から、内製化・開発文化の変革、生成AIの活用へと支援テーマが広がっている。

| 時期 | テーマ | 主な内容 |
|---|---|---|
| 2021～2022年 | モダナイゼーション | 性能課題を解決し、クラウドネイティブな形へシステムを刷新 |
| 2023年 | 人と組織を育てる | 内製化と開発文化の変革を進め、チームで学び、自ら開発できる状態を目指す |
| 2024～2025年 | AIで加速する | 生成AIを開発・業務に取り込み、開発者体験を向上 |
| 2026年 | AIで作る、AIが使う | 移行・運用そのものをAIで進めるとともに、AIが利用できる基盤へ刷新 |

事例として、ジェイアール東海情報システムによるサーバーレスでの設備異常通知システムの短期開発、中外製薬の「tech工房」による内製開発、NECによる複数AIエージェントを活用したリスク評価作業の効率化が紹介された。

#### AIエージェント向けデータベース

「AlloyDB PostgreSQL for agents」がPreviewとして紹介された。

- サンドボックス化されたデータベースインスタンスを数秒でプロビジョニングし、ゼロから数千ノードへ迅速にスケールアップする。
- 本番環境とは別の専用Colossusストレージセグメントから読み取ることで、AIエージェントのクエリによる本番処理への性能影響を抑える。
- エージェントの処理終了後はインスタンスが自動的にスピンダウンする。

ミッションクリティカルな処理の性能を維持しながら、AIエージェントによるリアルタイムのデータアクセスを支える構成が示された。

#### 既存環境の移行とモダナイゼーション

既存の仮想化・コンテナ環境をGoogle Cloudへ移行する選択肢が紹介された。

| 移行元 | 移行先として紹介された環境 |
|---|---|
| VMware | Self-managed VMware Engine（VCF 9.1） |
| Nutanix | NC2 on Google Cloud |
| OpenShift | Red Hat OpenShift Dedicated |

講演資料では、東京リージョンのGCE Z3 Baremetal上で、Self-managed VMware Engineは2026年9月Preview、NC2 on Google Cloudは2026年7月GAと紹介された。

既存環境の移行後、Compute Engine、Google Kubernetes Engine、Cloud Runなどを活用して段階的にモダナイゼーションを進める方向性が示された。

### 1.2 ロッテ

**ロッテが挑むAI駆動型変革**

登壇者：株式会社ロッテホールディングス 橋本 桂祐 氏

#### ICT部門の役割と変革戦略

ICT部門を、変革推進の中核を担う戦略的パートナーとして位置付け、次の4つを戦略の柱としている。

| 戦略の柱 | 内容 |
|---|---|
| 価値共創エンジン（攻めのIT） | テクノロジーとデータを活用して新たな価値を創造し、収益性向上に貢献 |
| 信頼されるデジタル基盤（守りのIT） | 安全で効率的なITインフラ・システムを整備し、事業運営を支える |
| エンパワーされた人材とデジタル文化 | コラボレーション文化を育み、従業員が活躍するための仕組み・ツールを提供 |
| サステナブルなデジタル化 | サステナビリティ目標の達成をITで支援 |

DX推進チームは、事業部門の課題解決を支援するパートナーとして、DX・AIをアジャイルに推進し、データ・AI駆動型の経営・事業活動の実現に貢献することをミッションとしている。

#### AI活用の段階的な拡大

AI活用を、個人の作業支援から業務の自動化、価値創出へと広げる考え方が示された。

| 段階 | 狙い | 業務例 |
|---|---|---|
| 人の作業のサポート | 検索・情報整理などを支援 | 類似事例の検索、議事録要約、社内FAQ・マニュアルの要点抽出 |
| 人の作業の代替 | 繰り返し・定型作業を自動化 | 請求書の自動読取・仕訳作成、帳票の出力・送付、問い合わせ対応 |
| 価値創出 | データを活用した提案・シミュレーション | 新商品の開発・企画、商品構成・価格の見直し、注力市場・顧客の特定 |

最終的な判断・実行は人間が担う方針が示された。

基盤整備については、以下の段階で進める構想が紹介された。

1. **データ・AI基盤作り**：全社ダッシュボード整備、生成AIの個人利用普及。
2. **AI-Ready化**：生成AIの社内接続、AIエージェント活用、非構造化データ収集。
3. **AI-Powered化**：データドリブン・AI駆動型の経営・事業活動へ展開。

#### 経営目標と連動した全社推進

従来の生産性改善では、足元の改善や従業員の意識醸成に成果があった。今後は2030年の経営目標を踏まえ、各領域で取り組む施策と、その目標実現につながるターゲットを設定する。

経営層をスポンサーとする全社プロジェクトのもと、研究、マーケティング、営業、SCM、生産、管理の各部門が参画。AI開発、グループ標準言語定義、AI・データ基盤構築を並行して進める体制が紹介された。

聴講時の説明では、5か年ロードマップに沿ってAI活用と数値による成果提示を求め、経営層が進捗を確認する運営や、トークン利用量の把握にも言及があった。

#### 事業部門との連携と内製開発

戦略的パートナーとして事業部門と連携するため、次の工夫が紹介された。

- **「Why」から入る**：作りたいものの要求だけでなく、「なぜ変えたいのか」を起点に業務の本質を確認する。
- **具体的なモデルで将来像を共有する**：企画の早い段階でMOC（講演資料表記：モック概念モデル）を可視化し、認識のずれを発見して合意形成を進める。
- **内製のアジャイル開発で成果を示す**：短いサイクルで現場に届け、見える成果を通じて信頼を得る。

部門からの個別リクエストへの対応だけでは、全体最適のアーキテクチャにはつながらないとの指摘があった。

#### データ・AI基盤の全体アーキテクチャ

データ・AI基盤は、UI、AI、セマンティック、データの各レイヤーで構成されている。

| レイヤー | 主な構成・役割 |
|---|---|
| UI | Gemini Enterpriseによるチャット、Cloud Run上のWebアプリ、Looker Studioなどのダッシュボード |
| AI | RAG、LLM、AI実行環境、エージェント通信制御、アクセス制御、MCP連携 |
| セマンティック | ナレッジデータ、ビジネスメタデータ、グループ標準言語定義を含む全社セマンティック管理 |
| データ | Google Drive・Cloud Storage・社内DBからデータを連携し、BigQueryへ蓄積 |

講演資料では、AlloyDBをAIが都度参照するキャッシュDBとして検討中とされていた。

Google Cloud中心の設計理由として、BigQueryによる大量データの高速・効率的な処理、SQLによる内製運用、利用量に応じた課金が挙げられた。また、データを自社に蓄積しながら、AI側の技術進化を取り込む考え方が示された。

## 2. ロッテ（15:20～15:50／Track 1）

**ロッテが挑むAI駆動型変革：基盤×ユースケース同時推進と内製開発の最前線**

### 2.1 モノづくり改革の背景と狙い

ロッテでは、AIを活用した生産性向上に向けて全社で9つの重要テーマを設定。その中でも、メーカーの根幹である「モノづくり改革」を最重要テーマとし、AI導入を機に業務プロセスそのものをゼロベースで見直している。

カカオショックなどによって原材料をはじめとするコストが上昇し、菓子カテゴリーでも値上げが進む中、価格に見合う付加価値が求められている。「安く、広く届ける」ことから、「価値で選ばれるモノづくり」への転換が必要とされた。

一方、現場では調整・報告や書類・管理業務に多くの時間を費やしている。

| 部門 | 講演で紹介された業務実態 |
|---|---|
| マーケティング本部 | 会議・資料作成・メール対応などの調整・報告が54.4％ |
| 中央研究所 | 書類・管理業務が52％、本来の研究開発は約20％ |

※出典：ロッテ社内業務実態調査（2026年4月）を基にした当日講演資料。マーケティング本部は工数構成比、中央研究所は業務構成比。

関連部署との調整や確認が重なることで開発・発売が遅れ、商機を逃すことが課題となっていた。また、創造的な業務に取り組みたい人材、特に部署間の調整を担う中間層の離脱にもつながる構造が指摘された。

### 2.2 AIに任せる作業の特定

従来の業務には、人による判断を必要とする部分と、慣習的に人が担ってきた作業が混在している。後者をAIで代替し、人が価値創出に使える時間を増やす考え方が示された。

| 業務例 | 従来の課題 |
|---|---|
| マーケティングのスケジュール管理 | 担当者ごとにExcelで管理し、進捗が本人以外に見えにくい。状況確認や締切調整、個別の連絡・リマインドが集中 |
| パッケージ表示の確認（版下確認） | 版下を紙に出力し、表示要請書と照合。原材料・アレルギー表示などを一文字ずつ目視確認する作業を年間数百回繰り返す |

プロジェクトではマーケティング・研究とICTが同じチームとして取り組み、ICTは業務変革を推進するパートナーとして参画した。

### 2.3 費用対効果で絞り込んだ6つのAIユースケース

マーケティング、研究、品質保証、生産、SCM、営業など、モノづくりに関わる部署を横断し、費用対効果を踏まえて6つのテーマに絞り込んだ。

| AIユースケース | 主な役割 | 講演時点の状況 |
|---|---|---|
| 全体ワークフロー管理AI | スケジュールで全工程をつなぎ、各AIを呼び出す | 本番リリース推進中 |
| 商品開発AI | 既存原料・過去の配合から提案 | 11月以降に本番リリースを推進 |
| 表示相談AI | 法規・内規に沿った表示相談への対応を即時化 | 本番リリース推進中 |
| 原料規格書確認AI | 原料規格書の不備・整合性を自動照合 | 本番リリース推進中 |
| イングレ確認AI | 原材料表示の計算を確認 | 11月以降に本番リリースを推進 |
| 版下確認AI | 表示内容と版下を自動照合 | 11月以降に本番リリースを推進 |

判断は人が担い、AIは作業を担う設計を基本としている。

### 2.4 共通基盤とユースケースの同時推進

共通基盤の完成を待たずにユースケース開発を進め、実際のデータ要件や現場の知見を基盤設計に反映する進め方が紹介された。

同時推進に当たっては、以下の2つが課題となった。

- **アプリ開発の実現性**：事業部門が求めるAI・Webアプリを内製で作れるか。どのような開発手法・プロセスが適切か。
- **安全に提供するための基盤整備**：作成したアプリを安心してリリースできるか。デプロイ、監視、権限、認証、セキュリティ、DBなどを共通基盤としてどう整備するか。

事業部門と将来像を共有してシステム構成図に落とし込み、具体的な検討事項を整理した。

| 検討領域 | 主な確認事項 |
|---|---|
| 共通UI（Webアプリ） | 開発方法、デプロイ先、認証、ワークフローデータの保存先 |
| UIとAIの連携 | UIからAIを呼び出す方法 |
| AIの実装・開発 | 開発方法、デプロイ先 |
| DB | 利用するデータベースの選定 |

### 2.5 TAPを活用した3日間の検証

ロッテのICT・事業部門、Google、基盤パートナーが共同で、3日間のTAPによる検証を実施した。

- ロッテのメンバーを主体としたバイブコーディングで、アジャイルにプロトタイプを構築。
- 事業部門も参加し、実務で利用できるかをその場で検証。
- 基盤パートナーと共通基盤のアーキテクチャを検討。
- 開発からデプロイまでの一連の流れを体験。

事業部門の意図を動くプロトタイプとして具体化し、実務で使える精度を確認できたことが成果として挙げられた。改善後の業務を具体的に示すことで、現場や上層部の理解・納得も得やすくなった。

ICT側では、バイブコーディング、ADKによるエージェント開発、アジャイル開発の進め方を習得。CI/CD設計の土台と、共通基盤アーキテクチャの方向性を得た。

### 2.6 原料規格書確認AIの構成と継続改善

原料規格書確認AIでは、現場のメンバーがGemini EnterpriseのチャットUIから原料規格書・別添PDF・画像をアップロードする。

| 構成 | 主な役割 |
|---|---|
| 統括エージェント（単一のroot_agent） | 原料規格書・別添の解析、チェック、再依頼文の生成を統括 |
| 決定論チェックエンジン（Python） | 200項目のチェックを実行 |
| チェックルールKB | チェックに用いるルールを管理 |
| チェック証跡 | 結果をスプレッドシートに保存 |
| 動作ログ | Cloud Loggingに記録 |

継続改善には「ループエンジニアリング」の考え方を採用している。

1. 現場で利用する。
2. 利用記録・ログを蓄積する。
3. AIが改善案を作成し、バイブコーディングでルールを修正する。
4. 人が承認・検証し、本番へ反映する。

人が下した判断を改善に取り込み、AIだけで処理できる項目・パターンを増やすことで、利用を重ねるほど作業負担を減らす方向性が示された。

### 2.7 共通基盤とAI組み込み型CI/CDの構想

共通基盤は、UI、AI、セマンティック、データの各レイヤーで構成される。2026年9月時点のアーキテクチャとして、以下が紹介された。

| レイヤー | 主な構成 |
|---|---|
| UI | Gemini Enterprise、Cloud Run上のWebアプリ、Looker Studioなど |
| AI | RAG、LLM、AI実行環境、エージェント通信制御、アクセス制御、MCP連携 |
| セマンティック | ナレッジデータ、ビジネスメタデータ、グループ標準言語定義 |
| データ | Google Drive、Cloud Storage、社内DB、iPaaS・Cloud Runによる連携、BigQuery、AlloyDB（検討中） |

今後は、ユースケースで必要になった機能を抽象化し、共通基盤の機能・作業として基盤チームのWBSへ反映する。

また、開発速度と安全性を両立するため、AIを組み込んだCI/CDを構想している。

1. バイブコーディングでAI・アプリを開発し、修正・再検証する。
2. チェックエージェントで、セキュリティ、品質、コスト・パフォーマンス、データガバナンスを確認する。
3. 検査結果とルールに基づいて基準への適合を確認し、必要な人の承認を得る。
4. 共通の経路で本番へデプロイする。

基準未達・未承認の場合は修正へ戻し、本番には進めない設計方針。エージェントが結果整理や修正を支援し、安心して開発を増やせる基盤を目指す。

事業部門、ICT、Google、基盤パートナーが一つのチームとして連携することが、持続的なAIユースケース推進に不可欠とされた。

部門・企業間の垣根を越えることで、ソリューションや運用の精度を高めるとともに、目的や熱意の共有によって現場の主体的な参画を促す。

## 4. KDDIアイレット（16:40～17:10／Track 3）

**なぜ自社独自MCPサーバーなのか？ BigQueryと進めるデータ基盤のAI-Ready化**

登壇者：KDDIアイレット株式会社 田村 直樹 氏／小林 千紘 氏

### 4.1 AI-Readyを実現する3つの条件

データを蓄積するだけでは、AIに業務を任せられる状態にはならない。本セッションでは、AI-Readyを実現する条件として「権限」「意味」「出力」の3つが示された。

| 条件 | 必要な状態 | 不足した場合の問題 |
| --- | --- | --- |
| 権限 | 利用者に許可された範囲でデータを取得できる | 閲覧を許可していない数字までAIが回答する |
| 意味 | 列や業務用語の意味をAIが理解できる | 用語や集計方法を取り違え、異なる数字を返す |
| 出力 | 結果を資料やスプレッドシートに出力できる | 回答を得ても、資料への転記が手作業で残る |

これらに対して、自社MCPサーバー、BigQueryの分析用ビュー・用語集、Skillsによる資料作成手順を組み合わせた取り組みが紹介された。

### 4.2 社内システム「超DX」の内製開発

案件や工数をスプレッドシートで管理していたが、管理の手間が大きく、既存パッケージでは自社固有の計算や細かな要件に対応しきれない課題があった。

当初は開発工数を確保できず、AppSheetで簡易アプリを作成していた。その後、AI駆動開発により少ない工数でも自社要件に合うシステムを構築できると判断し、「超DX」の開発を開始した。

- 2月末に開発を開始し、4月に運用開始。最低限の機能に絞り、約1か月で構築した。
- 開発手順を「Issue → 仕様 → 設計 → TDD実装 → PR → 人の確認」として定型化した。
- IssueからPRまでをAIと進め、最後は人が確認する。
- 業務ロジックと権限制御を自社で管理し、AI連携にも再利用できるようにした。

### 4.3 業務システムと分析基盤の構成

社員が利用する業務システムと、分析用AIが利用するデータ基盤を分けて構成していた。

| 構成要素 | 役割 |
| --- | --- |
| Cloud Load Balancing | 業務システムへのアクセスを受け付ける |
| Cloud Run | 「超DX」のWeb画面・アプリケーションを実行する |
| Cloud SQL | 業務データを保持する |
| Datastream | 業務データをBigQueryへ連携する。紹介時点では70モデル中11テーブルを対象としていた |
| BigQuery | 分析用データを保持し、Conversational Analyticsでの対話的な分析に利用する |

### 4.4 自社独自のMCPサーバーを開発した理由

DBへ直接接続する型の既製MCPでは、アプリケーションが持つ業務ルールやロール判定を別途実装する必要がある。

自社MCPでは、Web画面と同じ業務ロジック・ロール判定を呼び出すことで、業務ルールの二重管理を避けた。

| 観点 | 自社MCPでの対応 |
| --- | --- |
| 業務ロジック | Web画面と同じ業務ロジックをそのまま呼び出す |
| 権限制御 | Web画面と同じロール判定をツールごとに適用する |
| 認証・制限・監査 | 自社で実装・管理する |
| 保守 | 自社で責任を持つ |

MCPを単なるDB接続口とするのではなく、既存の業務ルールを適用する入口として設計していた。

### 4.5 MCPの構成と権限制御

紹介された開発環境では、社内VPNを経由し、Cloud Load BalancingとCloud Armorでアクセスを制限していた。

- Web画面用とMCP用のCloud Runを分離する。
- `/api/agent/*`へのアクセスをMCP用Cloud Runへ振り分ける。
- Cloud Runへの直接アクセスを遮断する。
- MCPクライアントとしてGoogle Antigravityを利用する。

MCP側では、次の順序で利用者と権限を確認する。

| 確認項目 | 内容 | 拒否時の扱い |
| --- | --- | --- |
| OIDC検証 | 署名、有効期限、audience、社内ドメインを確認 | 401 |
| 本人突合 | 有効な社員のみ許可し、退職・停止済みの利用者を拒否 | 403 |
| レート制限 | 1人あたり毎分30リクエストまで | 429 |
| 権限判定 | ツールごとに必要な最低ロールを確認 | 権限エラー |

実行の成否を監査ログに記録し、保存期間は90日としていた。OIDC検証や本人突合での拒否は、アプリケーションログに記録する。

案件・社員・稼働情報などの取得はメンバー以上に許可し、業務委託のロールからは呼び出せないなど、ツール単位でアクセス範囲を制御していた。

### 4.6 BigQueryのビューと用語集で業務上の意味を伝える

テーブル名や列名だけでは、AIに業務上の意味は伝わらない。そのため、BigQueryの分析用ビューに説明を付与し、Knowledge Catalogの業務用語集と組み合わせていた。

- 分析用ビューの説明で、計算式やデータ間の関係を示す。
- 業務用語集で、社内固有の言葉と定義を示す。
- 用語をテーブルや列に紐付け、AIが参照できるようにする。
- 複数の定義が存在する指標は、その違いも明記する。

| 用語 | AIが取り違えやすい点 | 用語集に記載した内容 |
| --- | --- | --- |
| 空き | 仕事がまったくない人だけと解釈する | 稼働が1人月に満たない人も含む |
| 実績 | どの計算方法による数字か判断できない | 複数ある算出方法を併記する |
| 稼働率 | 画面ごとに異なる定義の1つを使ってしまう | 画面ごとの定義を併記する |
| 受注見込み | ステータスが「見込」の案件だけを数える | 受注の確度が高い案件という意味を示す |

意味の説明をプロンプトだけに持たせず、データ側に整備することがポイントとして示された。

### 4.7 MCPとSkillsによる資料作成の定型化

AIが回答できても、スプレッドシートへの転記や資料の整形が手作業で残る。また、毎回ツールの使い方を指示すると、利用者によって出力形式がばらつく。

これに対し、データ取得はMCP、資料作成の手順はSkillsに分けて定義していた。

**処理の流れ：AIに依頼 → 自社MCPで取得 → Skillsで整形 → gws CLIで書き出し**

Skillsには、次の内容を記載する。

- MCPへの接続手順
- 資料の作成方法・出力形式
- gws CLIの利用方法

これにより、接続や出力の方法を毎回指示せず、誰が依頼しても同じ形式の資料を作成できるようにしていた。

### 4.8 空き人員の調査・資料作成のデモ

「手が空いている人は誰か」「空いている人をシートにまとめてほしい」という依頼を題材に、2つのデモが紹介された。

| デモ | 利用する仕組み | 確認するポイント |
| --- | --- | --- |
| 空き人数の調査 | BigQuery＋Conversational Analytics＋Knowledge Catalog | 社内で定義した「空き」の数え方を適用できるか |
| 空き人員のシート作成 | 自社MCP＋Skills＋Antigravity | 業務ルールと権限を適用し、資料への出力まで進められるか |

人数調査では、説明のない物理テーブルを参照するエージェントと、説明付きビュー・Knowledge Catalogの13語を参照するエージェントを比較していた。

「空き」は、休職・時短の分を差し引いた月の実効稼働が1人月未満であることと定義し、単純に案件がない人を数えるだけではない点を示していた。

### 4.9 セッションの要点

- **権限：** AIからのアクセスにも、既存システムの業務ルールと権限制御を適用する。
- **意味：** 解釈が分かれる業務用語や計算方法を、データ側の説明と用語集に記載する。
- **出力：** データを取得するツールと資料を作成する手順を分け、Skillsで出力を定型化する。

自社MCPの採用は、既存の業務ロジックと権限を再利用するための選択であり、保守責任も自社で持つという判断だった。

## 5. スタメン（17:20～17:50／Track 1）

**AWSからGoogle Cloudへのリアーキテクチャ！ AI SkillsとTAPで挑むAI駆動の基盤移行**

登壇者：株式会社スタメン 近藤 靖 氏

### 5.1 移行対象と既存基盤の課題

組織のエンゲージメント向上や業務DXを支援する「TUNAG」のモノリスサービスを、AWSからGoogle Cloudへ移行した事例が紹介された。

TUNAGでは、チャット基盤にGKE AutopilotとAlloyDB for PostgreSQL、サブサービスにCloud RunとCloud SQLなど、以前からGoogle Cloudを活用していた。今回の移行では、モノリスサービスの既存課題を解消するリアーキテクチャを実施した。

| 既存基盤の課題 | 内容 |
| --- | --- |
| 環境の境界 | 同じAWSアカウントに本番・ステージングが混在し、権限やリソースの境界を分けにくい |
| 運用負荷とコスト | ECS on EC2のインスタンスやオートスケーリングの管理に手間がかかり、コストにも無駄があった |
| 構成の複雑さ | CI/CDなどの構成が複雑で、インフラを扱えるメンバーが限られる |
| IaC化の不足 | 人だけでなく、AIにとっても既存構成を把握しにくい |

### 5.2 移行内容と実施結果

主要なサービスの移行先は次のとおり。

| 移行前：AWS | 移行後：Google Cloud |
| --- | --- |
| Amazon ECS on EC2 | Cloud Run |
| Amazon Aurora | Cloud SQL Enterprise Plus |
| Amazon ElastiCache | Memorystore for Redis |
| Amazon S3 | Cloud Storage |

移行作業は2026年7～9月の約2.5か月、実働2人月で進め、10月2日に本番環境を切り替えた。一部機能はAWSに残し、Google Cloudから連携する構成としていた。

| 項目 | 紹介された成果 |
| --- | --- |
| DB性能 | Cloud SQLのデータキャッシュを活用し、1リクエストあたりのDB時間が50%改善 |
| デプロイ | ビルドの改善などにより、デプロイ時間の中央値を18%短縮 |
| スケーリング | ECS on EC2で課題となっていたスケーリング待ちを改善 |
| コスト | Google Cloudチームとの利用計画策定と、費用の大きいモノリスサービスの移行により削減を実現 |

### 5.3 TAPによる段階的な検証と移行支援

Google Cloudチームとは2025年から継続的に議論し、TAP（Tech Acceleration Program）を通じて段階的に移行を進めた。

| 時期 | 取り組み |
| --- | --- |
| 2025年～ | TUNAGの課題をGoogle Cloudでどう解決できるかを議論 |
| 2026年5月 | 第1回TAPでサブサービスを対象としたPoCを実施 |
| 2026年7月 | 第2回TAPを実施し、移行作業を開始 |
| 2026年10月2日 | 本番環境を切り替え |

TAPでは、AIに任せる作業の順序と人が判断する箇所を実践的に習得した。また、次のような構成改善を具体化した。

- S3バケットを、用途ごとのCloud Storageバケットに分割する。
- 本番とステージングを別プロジェクトに分離する。
- ステージングを本番と同等の構成にする。

小さな対象で試し、計画と実現性を確認することが、本番移行に踏み出す根拠となった。

### 5.4 AI Skillsによる移行の進め方

Google Cloudチームから提供された移行用AI Skillsを利用し、調査から設計・生成までを段階的に進めた。前準備として、Terraformerで既存環境をIaC化した。

| フェーズ | 実施内容 |
| --- | --- |
| Discover | Terraformとソースコードから既存構成を洗い出し、構成図を生成する |
| Clarify | コードだけでは判断できない点を、人に質問して確認する |
| Design | Google Cloud上の構成を設計し、設計判断をADRに記録する |
| Estimate | Cloud Billing APIから取得した価格情報を使い、コストを見積もる |
| Generate | Terraform、移行スクリプト、アプリケーションの修正パッチなどを生成する |

AIが調査・設計・生成を担い、人が各フェーズの区切りで内容を確認し、判断する進め方としていた。

#### Clarify：コードから分からない意図を確認する

実例として、ECSで稼働するSidekiqについて、AIからトラフィックの流入元を問う質問が提示された。

公開HTTP、内部通信、HTTPを受けないバッチワーカー、定期実行では、移行先の構成が変わる。人が「バッチワーカー」と回答し、その情報を後続の設計の前提とした。

#### Design：既存構成を整理する

AIが生成した移行後の構成図をもとに、チームで次のような変更を判断した。

- nginx／Fluent Bitのサイドカーを廃止する。
- 定期実行用と手動実行用に分かれていたECSサービスを、Cloud Run jobsに統合する。

#### Generate：移行に必要な成果物を生成する

第2回TAPでは、初日に次の成果物が一通り揃った。

- Terraformコード
- 前提条件の確認、データ・コンテナ・シークレット・S3アセットの移行、移行結果の検証を行う6本のスクリプト
- アプリケーションの修正パッチ
- 設計判断を記録したADR
- 移行ガイドと移行レポート
- AWS SDKの呼び出しをGoogle Cloud向けに書き換えるPR

生成物は、人が一つずつ確認しながら実環境に適用した。

### 5.5 AIによる調査と、人によるコンテキストの補完

AIとの壁打ちで実現方法の候補を洗い出し、実装まで確認してから選択肢を絞ることで、手戻りを防いでいた。

例えば、AWSに残す機能をCloud Runから呼び出すための認証では、複数の方法を比較した。最終的にはSDKのクラスを拡張したcredential providerを採用し、メタデータサーバーのIDトークンを使って、Railsプロセス内でAWS STSから一時的な認証情報を取得する構成とした。

また、事前調査で見逃していた制約について、人が具体的な懸念を提示し、AIに影響範囲を調べさせた事例も紹介された。

- Cloud RunのHTTP/1におけるリクエストボディ上限として、32MiBを確認した。
- 人が「上限に抵触する箇所がないか」と問い直した。
- AIによる調査で、32MiBを超える画像アップロードを受け付ける既存実装が残っていることを発見した。

AIに任せる際も、プロダクト固有の事情や懸念を人が補う必要があることが強調された。

### 5.6 AI活用の工夫

| 工夫 | 目的・方法 |
| --- | --- |
| サブエージェントへの分担 | 観点ごとに調査を分担し、要約を受け取ることでコンテキストの肥大化を防ぐ |
| 一次情報の参照 | Google Developer Knowledge APIをMCPとして利用し、公式ドキュメントを参照させる |
| TerraformのSkill | planの確認やロールバック手順まで含め、インフラ変更を安全に進める |

### 5.7 移行後の開発基盤強化

#### サブサービスを立ち上げやすい基盤

従来は、サブサービスのインフラ構築コストが高く、新規立ち上げが止まっていた。また、実装のお手本がなく、セキュリティ水準を揃えにくい課題もあった。

Cloud Runの採用により、多くのユースケースでマネージドサービスの恩恵を受けられ、サービスごとにプロジェクトを分ける構成が組織に適していた。

今回移行したモノリスサービスの構成を標準構成として、次の取り組みにつなげる方針が示された。

- Terraformモジュールによるアーキテクチャのテンプレート化
- セキュリティ・権限管理の統一
- 共通コンポーネントの提供
- 移行で蓄積したAI活用方法の展開

#### PRごとのPreview環境

AI活用で開発が速くなる一方、検証環境の数やデプロイ時間がボトルネックとなっていた。

対策として、Cloud Runのリビジョンとタグを使い、PRごとに専用URLを持つPreview環境を立ち上げる構成が紹介された。通常のトラフィックを割り当てず、ゼロまでスケールさせることで、検証環境を増やした際のコストを抑える考え方だった。

#### BigQueryを中心としたデータ基盤

データ基盤についても、運用・保守コストと使いやすさの課題を解消し、BigQueryを中心とする構成へのリアーキテクチャが示された。

TUNAGに蓄積されたデータを顧客に還元するため、自然言語による分析や、AIエージェントからの参照を目指していた。

### 5.8 セッションの要点

- TAPで小さく試し、継続的な議論を通じて本番移行の実現性を確認する。
- AI Skillsで調査・設計・生成の手順を定型化し、人がフェーズごとに判断する。
- 既存構成の移行と併せて、環境分離・構成簡素化・標準化を進める。
- AIが把握しきれないプロダクト固有の事情は、人が具体的に補う。

AIを活用して少人数で移行を進めながら、移行後の開発生産性を高める基盤整備にもつなげた事例だった。

## 6. 所感

AI活用の拡大には、AIが解釈できるデータ、生成コードを安全に実行できる環境、エージェントのアクセス・通信を制御する仕組みを含めた基盤整備が必要と感じた。

ロッテの事例では、経営目標、事業部門のユースケース、共通基盤、標準言語の整備を並行して進めている点が参考になった。全体アーキテクチャを描きつつ、内製のアジャイル開発で具体的な成果を早期に示す進め方は、AI駆動開発・内製化推進を検討する上で示唆がある。

マクロミルの事例からは、開発速度の向上に向け、開発基盤・コア領域・SREなど、自社で担う領域を定めることの重要性を感じた。
